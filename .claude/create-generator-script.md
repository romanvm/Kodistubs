# Instructions for creating Kodistubs generator script

You need to create a Python script that generates Python stub packages for Kodi-Python API according to the following
specs:

## General

- The script should be placed in `kodistubs_generator` subdirectory relative to the project directory. The subdirectory
  should contain `__init__.py` file.
- The script may contain several Python modules depending on the needs.
- The script entrypoint should be located in `__main__.py` file.
- The script should be run as `python -m kodistubs_generator` from the project root.
- The script must accept an optional parameter that is a comma-separated list of Kodi-Python API modules that
  you need to generate stub packages for, e.g. `python -m kodistubs_generator xbmc` or
  `python -m kodistubs_generator xbmc,xbmcgui,xbmcvfs`. If the parameter is missing, generate all stubs.
- Generated stub packages should be placed in `src` subdirectory overwriting the existing content.
  Do not commit anything to Git without an explicit confirmation.

## Settings

The script package should include `settings.py` file with the following variables (paths are relative to the
project root):

- `KODI_SRC_DIR = '../xbmc'` — the root of the Kodi source checkout. All other Kodi paths are derived from it:
  - `{KODI_SRC_DIR}/xbmc/interfaces/swig` — SWIG interface files (`AddonModule*.i`, `kodi_*.i`).
  - `{KODI_SRC_DIR}/xbmc/interfaces/legacy` — C++ implementation of the Python API with Doxygen comments.
- `SWIG_EXECUTABLE = None` — path to the SWIG executable. If `None`, use the `swig` launcher installed next to the
  running Python interpreter (`sysconfig.get_path('scripts')`, so an unactivated venv works), then `swig` on `PATH`.
  SWIG 4.5.0 or newer is required (the same floor Kodi's `xbmc/interfaces/swig/CMakeLists.txt` enforces); fail with
  a clear message otherwise. Do not look for SWIG in Kodi build directories: they can be cleaned at any time.

SWIG is a project dependency: `requirements.txt` pins the `swig` PyPI package, which ships prebuilt SWIG
executables for Linux, macOS and Windows. Keep the pin equal to `tools/depends/native/swig/SWIG-VERSION` in the Kodi
sources (the SWIG Kodi itself builds with).
- `SWIG_WORK_DIR = 'build/swig'` — scratch directory for SWIG output. Must be git-ignored.
- `DOXYGEN_XML_DIR = 'doxygen/xml'` — Doxygen XML output directory.

## Source of truth for API structure: SWIG XML parse tree

Kodi no longer ships SWIG XML files: since Kodi 22 the bindings are generated by stock SWIG (4.5+) directly from
`xbmc/interfaces/swig/AddonModule*.i` (see `xbmc/interfaces/swig/README.md`). The SWIG-generated `*.pyi` files in the
Kodi build tree are incomplete (no constant values, read-only global constants such as `ACTION_*` are missing,
overloaded functions and all constructors are collapsed into `*args, **kwargs`, C++ default values) and must not be
used as the primary source.

Instead, the script must run SWIG itself for each module and capture the parse tree with `-xmlout`:

```
swig -python -c++ -builtin -interface <module> -pyi -w401,389,514,362,302
     -xmlout {SWIG_WORK_DIR}/AddonModule<Name>.i.xml
     -o {SWIG_WORK_DIR}/AddonModule<Name>.i.cpp
     -I{KODI_SRC_DIR}/xbmc
     {KODI_SRC_DIR}/xbmc/interfaces/swig/AddonModule<Name>.i
```

- Mirror the SWIG arguments from `generate_file()` in `xbmc/interfaces/swig/CMakeLists.txt`; `-xmlout` is the only
  addition. `-python` is mandatory: `-xmlout` dumps the tree *after* Python processing, so `%rename`, `%ignore`,
  `%extend`, `-builtin` operator slots, `%feature("kwargs")` and `pytyping` typemaps are already applied.
- The modules are `xbmc`, `xbmcaddon`, `xbmcgui`, `xbmcplugin`, `xbmcvfs`, `xbmcdrm`. Ignore `xbmcwsgi`.
- Regenerate SWIG output when the `.i` files or any header listed in the module's SWIG depfile (`-MMD -MF`) is newer
  than the cached XML; otherwise reuse the cache.
- `kodistubs_generator/swig_runner.py` implements the SWIG lookup (`find_swig()`) and the cached run
  (`run_swig()`).

When parsing the XML:

- Only collect declarations that come from `<include>` nodes for `interfaces/legacy/*.h`,
  `input/actions/ActionIDs.h`, `input/keymaps/keyboard/KeyIDs.h` and the module's own `AddonModule*.i`
  (for `%extend` and `%constant` blocks). Skip everything from the SWIG library and `kodi_*.i` files, the `std` and
  `swig` namespaces, and anonymous `%template()` instantiations (`__dummy_N__` classes).
- Skip any node with `feature_ignore` set.
- Descend into `<extend>` nodes: Kodi now adds Python-only methods there (e.g. `PlayList.__getitem__`/`__len__`,
  `File.__exit__`, `Action.__eq__`).
- Use `sym_name` (the Python name) rather than `name` (the C++ name) everywhere.
- Comparison operators that `-builtin` maps to Python slots (e.g. `Control.__eq__`, `__lt__`, `__gt__`) are part of
  the API and must be emitted.
- For overloaded functions/methods/constructors pick the most complete overload (most parameters, then most defaults).
- Constants come from two node kinds:
  - `<constant>` (`%constant`, `SWIG_CONSTANT*` macros, `SWIG_CONSTANT_FROM_GETTER`) — the `value` attribute holds a
    C++ expression (`CGUIListItem::ICON_OVERLAY_NONE`, `getLOGDEBUG()`, `static_cast<int>(SortMethod::NONE)`, ...);
    `numval` is present when SWIG already evaluated it.
  - `<cdecl kind="variable">` with `feature_immutable` (e.g. `constexpr const int ACTION_*` from `ActionIDs.h`) —
    these are exposed as read-only module attributes and have a `value`/`numval` attribute too.
  - Skip the module metadata strings (`__author__`, `__date__`, `__version__`, `__credits__`, `__platform__`).

## Constant values

Module-level constants must carry their real values. Prefer `numval` when present, otherwise resolve the `value`
expression against the Kodi C++ sources under `{KODI_SRC_DIR}/xbmc` (`getNAME()` accessors in
`interfaces/legacy/Module*.cpp`, scoped/unscoped enums, `#define`s, `constexpr` values, simple arithmetic).
The generated `.i.cpp` is only a debugging aid; do not parse it for constants.

## Type annotations

- Map C++ parameter and return types from the SWIG XML to Python annotations. The stubs target Python 3.10+, so use
  builtin generics (`list[str]`, `dict[str, str]`, `tuple[int, str]`, PEP 585) and union syntax (`str | None`,
  `str | ListItem`, PEP 604) instead of `typing.List`, `Dict`, `Tuple`, `Optional` and `Union`. Import from `typing`
  only what has no builtin form (e.g. `Any`, `TYPE_CHECKING`).
  Resolve typedefs (`XBMCAddon::String`, `XBMCAddon::Properties`, `InfoLabelDict`, ...) recorded in the XML.
- Kodi's own Python type intent lives in `xbmc/interfaces/swig/kodi_typing.i` (`pytyping` typemaps). The resolved
  return annotation is available as the `tmap_pytyping` attribute of each function node, and parameter annotations
  appear in the SWIG-generated `{SWIG_WORK_DIR}/<module>.pyi`. Use them as a fallback when the C++ type cannot be
  mapped, and report disagreements, but prefer precise Python types: `str` (not `str | None`) for `const char*`
  parameters that do not accept `None`, and bare class names for Kodi classes. Convert the `typing.List[...]`-style
  annotations Kodi uses to the builtin syntax above.
- Never leave `::`-separated C++ names in the generated Python.

## Docstrings: Doxygen XML

Docstrings for modules, classes, methods, and functions are taken from Doxygen XML generated from the
`///` comments in `{KODI_SRC_DIR}/xbmc/interfaces/legacy/*.h`. Do not parse C++ comments directly and do not use
SWIG's `-doxygen` mode: the documented declarations live in `#ifdef DOXYGEN_SHOULD_USE_THIS` blocks that SWIG never
sees, and the docs rely on Doxygen grouping (`\defgroup`, `\ingroup`, `@{ @}`), Markdown tables and code fences.

- The Doxygen configuration is `doxygen/kodi.doxy`; its `INPUT` must point at
  `{KODI_SRC_DIR}/xbmc/interfaces/legacy` and `PREDEFINED` must include `DOXYGEN_SHOULD_SKIP_THIS` and
  `DOXYGEN_SHOULD_USE_THIS`.
- If `{DOXYGEN_XML_DIR}` is missing or older than any `interfaces/legacy/*.h` header, run `doxygen kodi.doxy` from
  the `doxygen` directory before generating stubs.
- The top level XML files for xbmc* modules documentation are:
  * group__python__xbmc.xml
  * group__python__xbmcaddon.xml
  * group__python__xbmcgui.xml
  * group__python__xbmcplugin.xml
  * group__python__xbmcvfs.xml
  * group__python__xbmcdrm.xml
- Convert XML markup into the respective reStructuredText markup to preserve the semantical meaning of docstring
  elements: text style, parameters and return values descriptions, tables, admonition blocks, etc.
- Report every API member (from the SWIG XML) that has no matching Doxygen documentation.

## Output

- The generated stub packages must include all Python module-level constants, functions, classes, and methods exposed
  by Kodi to Python code and the respective documentation in valid reStructuredText format compatible with Sphinx
  documentation generator.
- Use existing src/xbmc* stub packages as an example of the output.
- Functions, classes, and methods must include call signatures with type annotations and minimal
  code not to raise syntax errors according to the following rules:
  * If a function or a method does not return anything, use `pass` operator.
  * If a function or a method returns a type, use a minimal instance of this type, e.g, an empty string for `str` type,
    and empty list for `list` type, `0` for `int` type, an instance of a class without parameters, etc.
- Parameter names must match the names SWIG exposes exactly: Kodi enables `%feature("kwargs")` for all modules, so
  addons may pass any argument by keyword.
- Fix unresolved references in type annotations and Python code to objects located in other stub packages.

## Verification

- Cross-check every generated module against the SWIG-generated `{SWIG_WORK_DIR}/<module>.pyi`: every function,
  class, method and parameter name in the `.pyi` must exist in the generated stub. Print a report of differences;
  the only expected extras in the stubs are read-only global constants that the `.pyi` omits.
- The Generated stub packages must produce correct Sphinx HTML documentation using the configuration in `docs`
  subdirectory. Fix all possible errors and warnings produced by Sphinx when generating docs.
